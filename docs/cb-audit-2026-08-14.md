## Region 2 — Meter helpers (L686-707) + applyMeterAccounts (L550-746)
`meterRemain/Used/Size`: Cycle* authoritative kalau `meterCyclePresent`, fallback Capacity* legacy. `parseFloatOr` fallback ke int field.
- **[MED] L686-707**: kalau Cycle field ADA tapi `CycleCapacityRemainPrecise` kosong + `CycleCapacityRemain=0` → return 0 = exhausted tanpa cross-check ke Capacity* (yang bisa 100). Cycle present = authoritative by design (dokumentasi 900d7df), jadi ini intentional — tapi flag kalau CodeBuddy mulai kirim Cycle kosong di akun sehat (dulu sempat terjadi).
- **[LOW] L711-725 parseCBMeterAccounts**: response `code != 0` / `Data.Response` null → `Accounts` nil → caller harus handle nil (applyMeterAccounts sudah guard `len==0` → return nil error). OK.
- **[LOW]**: applyMeterAccounts menulis key satu-per-satu — kalau meter API 500 (sedang terjadi), error di-log WARN massal (15+/menit) → log noise. Bukan bug, tapi noisy saat CodeBuddy degraded.

## Region 3 — DisableKey/EnableKey (L2330-2385) + toDTO (L287-317)
Persistent disable/enable: RLock scan → Lock mutate → saveCBKey(toDTO). disabledAt=zero (permanent), disabled_reason di-persist (fix ab07ab2), EnableKey reset semua.
- **[LOW] L2353/2381**: `saveCBKey(found.db, found.toDTO())` dipanggil SETELAH `found.mu.Unlock()` — toDTO tidak lock internal → race baca teoretis dengan mutator lain (credit-sync worker / Next() disable). Assignment string/bool atomic di Go → dampak praktis kecil. Kalau mau 100% aman: pindahkan `toDTO()` ke dalam Lock.
- **[LOW]**: `km.mu.RLock` scan → `found.mu.Lock` — dua lock terpisah tanpa urutan tetap (lock-order risk dengan path lain yang pegang `found.mu` lalu akses `km`). CleanupDisabled pegang `km.mu.Lock` + `k.mu.RLock` (urutan km→k, sama) → konsisten. Aman dalam praktik.
